# CrossLink AI 产品方案

本文说明目标产品设计。当前仅运行过MIT讲义的资料、知识审核、候选和报告基础流程；公开需求积累与技术匹配等目标功能尚未实现，具体边界见第六节。

## 一、总体目标与首个应用切口

总体目标：从不同领域的资料中发现有依据的连接，通过关系探索、多关系组合推理和反馈更新，提出可解释、可追溯、值得验证的创新机会。

首个应用切口：帮助有技术、但不清楚应用领域或升级方向的团队，将自身能力与分散的需求证据对照，发现可能的应用场景、能力缺口和验证方向。

首个场景是总体目标的具体落点。系统在此连接“需求方的任务与条件”和“技术方的能力与限制”，仍以跨领域关系探索为方法。未来可以扩展其他场景，本阶段先不同时覆盖研究选题、所有行业与全部日常需求。

## 二、用户与问题

目标用户是具备某项技术的小型研发团队、实验室或产品团队。需要验证的用户问题包括：

- 技术能够用于哪些实际任务，而不只是哪些行业名称？
- 公开求助中，哪些线索与自身能力有条件上的匹配？
- 当前不匹配的需求，分别卡在哪些能力或约束？
- 如果准备升级技术，哪些能力缺口有值得继续调查的需求证据？

这些是产品拟解决的问题，不表示已经证明团队愿意使用或付费。数据可得性、匹配质量和实际决策价值仍需真实试点。

## 三、保留的三个核心机制

| 核心机制 | 首个场景中的作用 | 应能展示的结果 |
|---|---|---|
| 关系探索 | 识别原始表达、任务、痛点、场景、技术能力和限制之间的关系 | 关系来自哪些原文或测试，哪些是AI推断 |
| 多关系组合推理 | 组合“任务需要能力→技术具备能力→条件是否兼容”等关系 | 可核对的匹配路径、冲突和证据缺口 |
| 反馈驱动改进 | 根据需求核实和技术测试修正对象、关系、条件与候选 | 新版为何改变，哪些旧结果受影响 |

“持续进化”在此首先指数据和判断随证据及反馈更新，不代表模型自动训练。是否改善，需要前后对比验证。

## 四、两条协同工作流程（目标设计）

### 流程A：持续积累需求证据

1. 从获准使用的数据接口、资料导入或其他允许的来源更新公开求助和评论；定时处理是目标功能，当前未接入平台。
2. 保存来源、时间、原文和上下文；识别转发及重复记录，无法确定是否独立时标记未知。
3. 提炼“谁在什么场景下，想完成什么任务，遇到什么阻碍，目前如何处理，有什么损失”。未表达的信息保持未知。
4. 按任务和关键条件归类，保留不同场景与反例，避免把相同关键词误并为同一需求。
5. 检查已有办法和未解决原因；标明检索范围与时间，不能把“未找到”当成“市场不存在”。
6. 更新可追溯的需求线索库，而非一次总结后固定不变的结论库。

“如果有个XX就好了”是需求线索和用户设想的解决办法，系统仍需核对其背后的实际任务。多人提到同类问题，可以增加观察证据；帖子数、点赞量和独立表达数均不能直接推算市场规模。沉默用户是否同样受影响，也不能由网络表达直接确认。

### 流程B：技术团队查询应用与升级方向

1. 团队简要介绍技术；系统追问输入、输出、精度、速度、成本、运行环境和不支持情况。
2. 能力与限制由团队确认，保留说明或测试依据；未知参数不得由AI补造。
3. 用任务与条件检索需求库，分别对照能力已满足、条件冲突和关键未知。
4. 形成三类结果：可能应用机会、待评估能力缺口、暂不推荐或需补证据。
5. 每条结果展示需求原文、技术依据、组合推理、反例与下一步验证办法。
6. 记录团队测试和需求核实反馈，更新后续结果。实际联系用户、测试和部署由团队在相应授权范围内开展。

## 五、完整设计案例：仪表读数录入与图像识别技术

**以下需求表达、编号、技术条件和反馈全部是虚构设计示例，未实际采集、访谈或测试，也不是已验证的创新或商业机会。**

### 1. 输入与需求分组

| 编号 | 假设的原始资料 | 应保留的判断 |
|---|---|---|
| S-01 | “现场没网，每天要把仪表数字手工录入，约两小时。” | 有损失描述和离线条件，但独立性、规模与实际工作量待核实 |
| S-02 | “办公室能联网，仪表没导出接口，仍要反复录数字。” | 同属读数录入任务，联网条件不同，不能与S-01合并为完全相同场景 |
| S-03 | “我们每周只录几项，手工很方便。” | 反例：类似任务不一定有强需求，不应自动列为目标用户 |
| T-01 | 团队确认：“能识别清晰印刷数字，可批量处理，目前必须联网；手写不支持，反光照片表现未知。” | 技术能力与限制，尚需实际样本验证；不从宣传语推断适用所有环境 |

系统按任务建立关联，但将N-01“无网络现场录入”和N-02“可联网办公室录入”作为不同条件组。上述少量示例不足以证明共同需求规模和采用意愿。

### 2. 关系探索与组合判断

需求表达 → 具体读数录入任务 → 需要识别能力及场景条件 → T-01是否满足 → 应用或升级假设。

| 结果 | 理由 | 还需要什么 |
|---|---|---|
| N-02进入样本验证 | 任务可能适合清晰印刷数字识别，且允许联网 | 实际图片、准确率、纠错时间、成本及用户采用条件 |
| N-01当前不匹配 | 现场要求离线，T-01当前必须联网，存在硬性冲突 | 不得直接推荐当前技术解决该场景 |
| 离线运行列为待评估升级方向 | 若获得可靠的N-01类需求证据，解除联网限制可能打开用途 | 核实需求强度、设备性能、离线准确率和开发成本；不能直接判定值得开发 |
| S-03不优先推荐 | 已有处理方式轻便，未显示明显损失 | 保留反例，不因技术能够处理就认定用户需要 |

这里的跨领域连接是需求任务、业务流程和图像识别能力之间的条件匹配。技术相似、原文存在或候选可解释，都不等于技术适配、需求真实或商业成功已经成立。

### 3. 输出长什么样

每张机会卡包含：目标人群与任务、需求证据与时间、当前解决办法、技术能力及限制、匹配路径、条件冲突、未知项和验证建议。

升级建议额外列出：能力缺口、关联需求组、原始证据、解除限制后仍存在的障碍及验证成本。它应帮助团队判断下一步查什么，不自动替代团队决定研发投入。

### 4. 反馈如何改变下一次结果

假设团队用获得授权的办公室样本测试后反馈：“许多图片有反光，纠错后比手工还慢。”

| 环节 | 反馈前 | 反馈后的下一版目标 |
|---|---|---|
| 需求判断 | 读数录入可能耗时 | 保留原始问题，不能因当前技术失败就否定需求存在 |
| 能力判断 | 反光处理未知 | 记录该批测试条件、结果及适用范围，不泛化成全部场景均失败 |
| 匹配判断 | N-02可进入样本验证 | 将受相同反光条件影响的匹配标为需修订，保留不受影响的场景 |
| 下一步 | 比较识别准确率和处理时间 | 评估图像获取方式或反光处理是否可改善，并重新比较总人工负担 |
| 历史 | 保存候选与输入快照 | 保存反馈、受影响关系、修订原因和新版本；不静默覆盖旧结果 |

这说明反馈要改变后续判断，而不是只改变报告措辞。前后效果需用可比任务和样本检验；本方案未提供已完成的对比结果。

## 六、当前实现与后续设计

| 环节 | 当前MIT原型 | 首个应用需要新增 |
|---|---|---|
| 数据输入 | PDF上传、按页阅读 | 获准使用的需求数据来源、更新任务及技术说明 |
| 信息提取 | 指定三页知识与原文引句 | 需求任务、条件、损失、技术能力与限制 |
| 审核 | 知识确认或拒绝 | 需求线索核对、能力追问及团队确认 |
| 关系与推理 | 候选引用已确认知识 | 显式关系、条件匹配、组合路径与冲突检查 |
| 输出 | 单一讲义的3条候选、报告下载 | 应用机会、能力缺口和暂不推荐的原因 |
| 反馈 | 来源状态变化提示 | 需求核实和技术测试结果、版本与影响传播 |

当前程序没有自动采集公开平台、定时需求积累、需求归类、技术追问、真实技术匹配或升级建议功能。MIT案例是基础流程验证；本节仪表案例是设计说明，两者不能混同。

## 七、与现有框架的关系

目标数据链为：来源记录→证据→任务与条件→技术能力→匹配关系→组合路径→机会或能力缺口→反馈更新。

原始的对象、关系与编排思路保留：用数据对象承载来源、任务和能力；用带证据的关系表达需求与能力的连接；用编排组织积累、提取、核对、匹配和反馈。具体字段与状态见[数据关系与编排设计](DATA_RELATIONS.md)。老师框架的实际接口仍需核实，当前未完成集成。

## 八、后续验证顺序

1. 补齐基础样本恢复，明确新环境如何运行演示。
2. 选择一个细分任务、可靠数据来源和真实技术团队，人工核对一批需求与能力记录。
3. 比较系统匹配与人工判断，记录错误合并、遗漏条件和假机会，验证是否帮助团队作出更好的判断。
4. 核心判断有效后，再扩展持续更新、更多领域与反馈传播；批量审核和详情展开保留为后续体验优化。
